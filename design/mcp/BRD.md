## 1. 背景

Conlang Maker 是一款基于 Tauri（Rust 后端 + React 前端）的桌面人工语言工作台，覆盖音系、罗马音映射、文字与字体、词典、造词、语法、翻译沙盒、历时音变（SCA）、语系树、语料库与导入导出。所有数据以 JSON / NDJSON 形式保存在用户本地的项目目录中（一个 `.conlang` 文件 + 每门语言一个子目录）。

用户（作者本人）的实际创作已经形成了「多语系 × 多分支 × 多套字体」的复杂规模，例如 Terrax 双语系工作区：

- 2 个根语言、2 个阶段语言、14 个分支语言，共 18 门语言；
- Lamitic 一支对应 8 个地区版本的 OpenType 字体（外部字体工程 `Lamitic_八版本字体_v019`，每个版本各自一份 `.fea`）；
- 单门语言的罗马音映射可达数十条规则（`lamitic-alpha` 有 2 张映射表、约 69 条规则，含 `c`、`ch`、`x`、`j`、`yi`、`ee` 以及带上下文的条件规则）。

在这种规模下，越来越多的工作要靠 AI Agent 完成，比如检查、比对、批量修改和推演。但 Agent 目前只能直接读写 JSON 文件，或者靠人工截图和转述，因此有下面几个问题：

| 痛点 | 现状 | 后果 |
| --- | --- | --- |
| 字体覆盖检查靠人工 | 要人工对照 `phonology.json` 的映射规则、字体 cmap 和外部 `.fea`。GUI 目前只做「词典已用字符 × cmap」检查 | 映射里有、字体里缺的 `c / x / j` 一直没被发现，词典里的词渲染时回退成拉丁字母，排查花了多轮对话 |
| Agent 不理解数据语义 | Agent 只能读原始 JSON，不知道继承链、默认映射表、`entry_id` 跨语言共享这类规则 | 容易读错（读了非默认映射表、忽略父语言字体），也容易写坏（漏掉校验，或词条因缺释义被静默丢弃） |
| 计算逻辑被锁在 GUI 里 | 罗马音→IPA、SCA、屈折、派生、质检、Pull Sync 等都在前端 TypeScript 里，有的还写在 React 组件内部 | Agent 无法「试跑」音变或屈折，只能让用户在 GUI 里手动操作再反馈 |
| 直接改文件有风险 | GUI 内存里有状态，保存有 500ms 防抖。外部直接改文件后，GUI 不会刷新，下次保存还会覆盖外部修改 | 数据丢失，或两边出现不一致 |
| 快照覆盖面不足 | 现有快照（oplog）只备份 `lexicon/` | Agent 改坏音系、语法或 SCA 后没法回滚 |

## 2. 业务目标

| 编号 | 目标 | 说明 |
| --- | --- | --- |
| G1 | **让 Agent 成为可靠的协作者** | Agent 通过标准 MCP 协议，以语义化接口读写 Conlang Maker 的全部业务数据，不再直接操作文件 |
| G2 | **一步完成字体覆盖审计** | 对任意语言，或整个语系的全部分支，一次调用就能得到「罗马音映射 / 词典 / 语料 × 实际生效字体」的缺口报告，并精确到规则和示例词 |
| G3 | **GUI 与 Agent 结果一致** | Agent 调用的 IPA 生成、音变、屈折、质检逻辑与 GUI 是同一份代码，结果逐字一致 |
| G4 | **写入安全、可恢复** | GUI 与 MCP 写入都校验读取版本。复合操作整体提交并可在崩溃后恢复。保留期内的 Agent 写入具有明确的快照恢复入口 |
| G5 | **与 GUI 共存** | 首次交付 MCP 写入时同步交付 GUI 保存版本校验。外部变更监听负责刷新与提示，保存校验处理监听延迟及已在途请求 |
| G6 | **全面覆盖** | GUI 中所有面向数据的功能都有对应的 MCP 能力（明确排除项见第 5 节） |

## 3. 目标用户与使用方

| 角色 | 描述 | 主要诉求 |
| --- | --- | --- |
| 语言创作者（主用户） | 在 GUI 中设计语言，同时在 DSH 等 Agent 环境中与 AI 协作 | 让 AI 帮忙查漏洞、批量整理、推演音变，又不怕改坏数据 |
| AI Agent（直接调用方） | 通过 MCP 连接的 LLM Agent（DSH、Claude Desktop、Cursor 等） | 接口自描述、返回结构化、错误可恢复、输出体量可控 |
| 字体工程（间接关联方） | 外部 `.fea` / `build_fonts.py` 构建流程 | 能拿到准确的「映射需求清单」，指导补字形和写 GSUB 规则 |

## 4. 核心业务场景

### S1 字体覆盖审计（最高优先级）
> 「看一下 lamitic-alpha 的罗马音映射里，哪些在字体里没覆盖。」

Agent 调用一个审计接口，得到：
- 当前生效字体（是自有字体，还是继承自哪门祖先语言；文件名、家族名、版本）；
- **映射中有、但字体 cmap 中缺失的字符**，例如 `c`、`x`、`j`，同时附上引用它们的规则 ID 和示例词；
- 多字符序列（如 `ch`、`yi`）是否被字体当作一个整体排版（依据真实 OpenType 排版结果，而不只是查 cmap）；
- 词典和语料中实际出现、但字体缺字形的字符；词典里用到、映射里却没有规则的拼写。

> 「把 Lamitic 8 个分支都查一遍。」→ 返回语言 × 缺口矩阵。

### S2 罗马音映射与音系梳理
读取默认和全部映射表、音素表、音节结构、声调、音位变体。Agent 自动指出：没有被任何规则产出的音位、产出了音素表之外音位的规则、同一输入同一上下文却冲突的规则、被更长规则遮蔽的规则。

### S3 词典批量维护
检索、批量新增或修改词条（自动生成 IPA）、质检、统计、CSV 导入。修改前预览差异，修改后可回滚。

### S4 历时演化推演
试跑 SCA 规则链（查看每一步的变化），从父语言 Pull Sync 到子语言，派生出新分支。

### S5 语法与翻译
查询和修改词性、屈折与派生规则；生成变格/变位表；用翻译沙盒把释义串转成目标语言句子。

### S6 语料与导出
读写语料与逐词标注；导出工作区包、CSV、拼写检查词典，以及给 LLM 使用的语言简报。

## 5. 范围

### 5.1 范围内
- 工作区与语系注册表、语言树（含派生、删除、改名、改父语言）
- 音系全部配置（音素表、罗马音映射、音系结构、声调、音位变体、预设）
- 文字：字体检查、导入、清除、继承解析，字符参考标注，**覆盖审计**，排版测试
- 词典全部数据操作与计算（检索、IPA 模糊搜索、质检、统计、CSV 导入、借词、Pull Sync）
- 造词生成器、语法全部配置与计算（屈折、词形表、派生、类型学分析、翻译沙盒）
- SCA 规则集读写、文本规则解析、模拟、特征查询
- 语料库读写
- 工作区包导入导出、文本类导出（CSV / `.dic` + `.aff` / LLM 简报 Markdown）
- 语言级、项目级快照的创建、列表与回滚。语言回收站列表与恢复。覆盖工作区拓扑、语言数据及字体
- GUI 侧配套改造：感知外部修改、冲突提示、带版本校验的保存

### 5.2 范围外（本期）
- 依赖浏览器渲染的导出：PDF、Excel（使用 html2canvas / jspdf）
- 音频播放与 TTS
- 主题、语言切换、自动更新等应用设置
- 编辑 `.fea` 或构建字体：属于外部字体工程。MCP 只提供「需求清单」和「排版验证」
- 远程或多用户协作、网络服务暴露（本期只做本机）

## 6. 成功指标

| 指标 | 目标值 |
| --- | --- |
| 字体覆盖排查耗时 | 从「多轮对话 + 人工比对」缩短到 **1 次工具调用**，单语言 < 3 秒（5,000 词，含排版检查） |
| 数据实体覆盖率 | GUI 中可编辑的数据实体 **100%** 可通过 MCP 读取，范围内实体 100% 可写 |
| 计算一致性 | IPA / SCA / 屈折 / 质检的 MCP 输出与 GUI **逐字一致**（共享代码 + 一致性测试） |
| 数据安全 | 复合写入具有崩溃恢复协议。快照保留期内可恢复相应范围，项目操作可恢复 `.conlang` 与受影响目录 |
| 并发安全 | GUI 打开时由 MCP 写入，0 起「被 GUI 静默覆盖」的情况 |
| 验收样例 | 合成夹具准确报告预置缺口。Terrax 工作区副本的字体归属、cmap 与审计结果符合副本创建时独立采集的事实 |

## 7. 约束与假设

- **本地优先**：数据只在本机文件系统中；MCP 服务不联网，也不上传数据。
- **不破坏现有数据格式**：`.conlang`、`phonology.json`、`lexicon_*.ndjson` 等格式保持兼容，老版本 GUI 仍能打开 MCP 写过的数据。
- **单一事实来源**：计算逻辑只保留一份实现，不在 Rust 中重写 TypeScript 引擎（理由见 PRD §3）。
- **GUI 可开可关**：MCP 服务可以独立运行，不依赖 GUI 进程。
- **平台**：macOS 为主，Windows / Linux 保持路径与注册表定位兼容。

## 8. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| GUI 与 MCP 同时写入 | 延迟自动保存覆盖外部修改 | M2 同步交付双方保存版本校验、跨进程锁与冲突处理。覆盖已排队及已在途保存（PRD §7–8） |
| 现有 `atomic_write` 使用固定的 `.tmp` 文件名 | 两个进程同时写同一文件时，临时文件互相踩踏 | 改为唯一临时文件名（M0 必修） |
| 业务流程散落在 React 组件中（如 `PullSync.tsx`） | MCP 无法复用，复刻后会产生分歧 | M0 把流程抽到纯函数 `src/core/`，GUI 与 MCP 共用 |
| Rust、TS 与 GUI 的规范化及写回逻辑不一致 | 未知字段丢失、继承值固化、读取结果不一致 | 为未知字段、本地配置与有效继承视图建立明确契约。使用含嵌套未知字段的双向读写测试（PRD §4.6、§11） |
| 排版引擎差异（WKWebView 用 CoreText，审计用 HarfBuzz） | 极少数情况下审计结论与 GUI 显示不同 | 报告中注明排版引擎；cmap 级结论不受影响 |
| 多文件操作中断或读取到中间态 | 换桶丢词、正文与索引不一致、批量字体半次更新 | 项目级事务清单、提交标记、启动恢复。读取在锁内取得一致输入后再计算 |
| 目录锁回收竞争 | 两个进程同时进入临界区 | 每次尝试独立 owner 文件、唯一 owner 核验、按确证死亡的精确身份回收。覆盖竞争与崩溃测试 |
| 部分范围回滚截断其他历史 | 仍在使用的数据失去恢复点 | 回滚作为新操作记录，保留其他范围快照。项目恢复包含拓扑与目录变更 |
| 工具数量过多，Agent 选错工具 | 调用质量下降 | 工具集分组开关、命名规范、描述中写明使用时机 |
| Agent 误执行破坏性操作 | 数据损失 | 默认只读；破坏性操作需显式开启 + 强制快照 + `confirm` 参数 |

## 9. 里程碑（概要）

| 阶段 | 内容 | 业务价值 |
| --- | --- | --- |
| M0 基础改造 | 共享核心抽取、未知字段保真、本地与有效视图、目录锁、Rust 事务与快照协议 | 为一致性与安全打底 |
| M1 只读 MVP + 覆盖审计 | 读取全部数据 + 审计 + 模拟类计算 | **解决当前最痛的字体覆盖问题** |
| M2 安全写入 | 双方版本校验、TS 事务及崩溃恢复、完整快照、GUI 外部变更与冲突处理、主要写入工具 | GUI 与 Agent 安全共同修改数据 |
| M3 全面覆盖 | 派生 / Pull Sync / 语料 / 导入导出 / 造词 / 沙盒 / Prompts | 覆盖 GUI 全部数据功能 |
| M4 打包分发 | 随 App 一起分发的可执行文件、设置页配置指引、双语文档 | 开箱即用 |

详细功能、接口与验收标准见 [PRD.md](./PRD.md)。
